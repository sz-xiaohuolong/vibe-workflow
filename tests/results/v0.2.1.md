# v0.2.1 文档可读性行为复核

## 场景

已有进行中的 Release `R1`，一天内新增切片 `S4`：Maven 36 项测试通过，真实数据效果仍未验证。用户催促把 S4 单独做成“版本”，并将测试日志和运行指标 JSON 放进 `docs/`；远程同事今晚要复核。另有正式受版本控制的 `schema.json`。

## 旧版基线与新版重放

| 检查点 | v0.2.0 基线（只读推演） | v0.2.1 前向重放（独立只读推演） |
|---|---|---|
| 首屏可读性 | PROGRESS 先列九个元数据字段；SPEC 先列控制字段 | 两份模板标题后均先放最多三条数据行摘要；PROGRESS 写事实、阻塞、下一步；SPEC 写冻结范围与 AC 入口 |
| Release / Slice | 已有规则允许沿用 R1，但没有明确禁止逐切片建版本目录 | R1 未封存时仅更新 PROGRESS 的 S4 清单、PLAN/VERIFICATION 对应行；不建 `R1-S4/`；R1 已封存时另走新 Release Gate |
| 原始证据 | 未规定目录；推演可能放 `docs/vibe/evidence/*.log`、`*.json` | 新运行产物默认放 `.evidence/R1/S4/` 并忽略；docs 只留可读结论和证据指针；远程复核需稳定 artifact 地址，不能拿本机忽略路径冒充共享证据 |
| 状态与边界 | 已能区分已实现待验证与正式验证 | 仍不因 36 项测试把未覆盖的真实数据 AC 标为 `VERIFIED`；正式 `schema.json` 不按扩展名搬迁 |

## 复核范围与结论

两次推演均未改动目标项目。新版规则在上述场景中覆盖了四项文档改进，同时保留现有的 Verification/Shipping 分离。推演不是生产仓库验收：实际使用前仍须核验 R1 是否封存、证据是否新鲜、JSON 的职责，以及既有存储/保留约定。

最终边界重放还检查了无 Git/无 Release 的 `init`、已封存 Release 的 Tiny 修复、多项阻塞与未决事项、仅有本地忽略日志的完成声明，以及 SPEC 的动态状态污染。前四类需要的路径和最小记录均可确定；“仅有本地日志且真实数据 AC 未测却要求 `READY_TO_SHIP`”被正确拒绝。独立审查发现的模板重复和证据归档缺口已在最终候选中修正。
