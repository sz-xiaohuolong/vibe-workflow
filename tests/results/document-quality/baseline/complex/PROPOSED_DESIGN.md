# 方案设计 — R3 后台上传

## 方案控制与决定依据

- 方案标识：`DESIGN-R3`；目标版本：`R3`；关联范围：`REQ-001` 至 `REQ-006` 及对应 AC。
- 方案状态：`APPROVED`，指输入中已确认的单一后台队列、双页面共享订阅、复用 API 适配层方向及既有契约；本文件展开其内部实现设计，尚未实现。
- 批准来源：[INPUT.json](INPUT.json) 的 `baseline`、`approved_contract`、`chosen_direction`；未提供批准人姓名和具体批准时间，不作补写。
- 内部实现由执行 Agent 负责；若改变产品、公开 API、权限、文件格式或新增持久化，须先提出范围变更。
- 更新日期：2026-10-20。

## 当前事实与目标

当前系统只有本地文件列表和详情页，尚无正式后台队列。上传 API 仅有隔离探针；夹具既有 `E-02` 的范围是 API 接受取消与幂等键。目标组件、状态机和订阅协议均是待实现方案，不能据此更新为已集成架构。

本方案要使任务不依附页面生命周期，所有状态更新可排序、可拒绝过期事件，并以保守的在途请求计数保证最大并发 2。失败可由用户恢复，本地原文件始终不变。

## 组件与数据流

```text
本地文件列表 ─┐
             ├─ 用户命令 → 后台上传队列 → 现有 API 适配层 → 既有上传 API
本地文件详情 ─┘                  ↑                │
       ↑                        └─ 带尝试标识的响应 / 取消结果
       └──── 相同任务快照与有序状态广播 ──┘
```

| 目标组件 | 责任 | 写入边界 |
|---|---|---|
| 后台上传队列 | 创建任务、串行接受事件、调度、取消、重试、认证暂停、广播 | 任务状态唯一写入者 |
| 内存任务记录 | 保存任务身份、创建顺序、文件引用、幂等键、当前状态和版本 | 仅队列可修改；不落盘 |
| 请求尝试记录 | 标记当前尝试、取消句柄和在途名额 | 由队列与适配层完成事件协作管理 |
| 现有 API 适配层 | 复用上传、取消、认证错误识别和幂等参数传递 | 只报告结果，不直接写任务或页面状态 |
| 列表与详情订阅 | 读取快照，展示状态，发送用户命令 | 页面不维护另一套可写任务状态 |

队列在应用级运行上下文中仅建立一次，页面挂载、卸载与切换不重建队列。这里的“后台”是应用运行期间独立于页面的队列，不引入常驻系统服务或应用关闭后继续上传的承诺。

## 内部契约与不变量

以下字段与命令是拟采用的内部契约，真实模块名和文件位置由实施时沿用项目习惯确定。

| 记录 | 最小信息 | 用途 |
|---|---|---|
| 任务 | 任务标识、单调创建序号、本地文件引用、幂等键、状态、错误摘要、状态版本 | 持续关联同一任务与原文件；为排序和订阅提供依据 |
| 尝试 | 任务标识、尝试序号、队列实例标识、取消句柄、结束标记 | 排除前次尝试和旧实例的迟到事件；名额只释放一次 |
| 队列 | 任务集合、在途尝试集合、认证暂停标记、等待用户继续标记 | 最大并发约束和认证恢复边界 |

内部命令为创建、取消、失败重试、登录状态更新、手动继续、订阅与解除订阅。命令进入同一个事件处理顺序；重复命令按当前状态处理，不能同时启动同一任务两次。

必须始终满足：

1. 任务状态只有队列可写；每次已接受的变化递增版本并产生一份不可变快照。
2. 在途请求数不超过 2；同一任务至多存在一个尚未结束的尝试。
3. 每次调度选择可运行任务中创建序号最小者；重试沿用原任务和创建序号，不抢占已在途任务。
4. 幂等键在任务创建时生成一次，同一任务的失败重试与认证继续沿用；尝试序号每次重新发起请求递增。
5. 成功、已取消是终态；失败只能由手动重试离开。认证继续只恢复因认证暂停的任务。
6. 没有文件删除、移动、格式变换或写回分支；队列不持久化任务或幂等键。

## 调度、取消与竞态处理

### 有序启动与名额

调度器检查认证可用、未处于等待继续状态，再从排队任务中按创建序号取任务。在调用适配层之前先登记尝试并占用名额；同步抛错也必须进入同一结束处理路径。结束事件只结算一次，再调度下一项。

逻辑上的已取消或暂停不等于底层传输已经结束。取消后，直到适配层报告本地请求结束才释放其名额；不能仅因按钮点击就复用名额，否则取消迟滞时可能出现第三个在途上传。若底层取消长期不结束，后续吞吐会下降，应记录适配层诊断并保留该名额；不以无条件超时释放换取表面进度。

### 取消的线性化点

队列接受取消命令并写入已取消状态，是本地取消生效点。对排队任务直接移出可调度集合；对上传中任务先提交已取消状态、广播，再向适配层请求取消。取消确认失败或迟到均不能撤回此状态。

响应到达后，先结算匹配尝试的在途名额，再检查是否仍有资格更新任务：队列实例、任务标识、尝试序号须一致，任务仍处于可接受结果的上传状态。已取消、已暂停或已被新尝试取代的结果只允许完成名额清理，不允许写任务结果。

| 事件顺序 | 队列处理 | 可观察结果 |
|---|---|---|
| 排队取消 → 调度 | 取消先移出候选集合 | 无请求，已取消 |
| 上传取消 → 成功迟到 | 成功只结束旧尝试，不写结果 | 保持已取消 |
| 成功已提交 → 取消 | 终态不接受取消转换 | 保持成功，返回当前结果 |
| 连续取消 / 多个结束回调 | 取消幂等；尝试结束只结算一次 | 不重复广播有效转换，不产生负数名额 |
| 旧尝试回调 → 已启动的新尝试 | 尝试号不匹配，拒绝写任务 | 新尝试结果不被覆盖 |

### 失败与幂等重试

普通失败记录为失败，保留同一任务和幂等键，不安排计时器或网络恢复重试。用户重试命令只对失败状态有效；一次状态转换即可使后续重复点击失效。若旧请求仍未结束，即使任务已回排队，也须等待该尝试结束后才能重新发起。

服务端可能已成功创建资源而客户端丢失响应，因此重试不能生成新键。适配层须原样传递既有键，并在真实接口集成中验证同一键返回同一资源或契约允许的同一结果。`E-02` 仅证明参数可接受，不能替代此验证。

## 认证暂停与恢复

1. 将现有适配层识别到的令牌过期事件转给队列；先关闭调度，再把非终态待执行任务标记为暂停，并广播登录提示。
2. 对仍在途尝试发出取消以停止本地传输，保留原幂等键和名额直到请求结束；失去状态更新资格的迟到响应不能恢复上传。
3. 已成功、已取消保持原终态，普通失败仍为失败。认证暂停不会把失败任务变成可自动继续的任务。
4. 登录成功仅解除认证无效标记，保留“等待用户继续”；只有继续命令才能把认证暂停任务放回排队。
5. 恢复时按原创建顺序调度，并先等待尚未结束的旧尝试；再次过期则重复暂停。未登录的继续命令不发请求。

暂停不承诺断点续传；继续通过既有上传 API 重新尝试并沿用键。登录与令牌保管沿用现有机制，队列不新增权限、不自行刷新或记录凭证。具体认证错误映射和本地请求结束语义须在 API 集成任务中核对。

## 双页面一致性

订阅必须在队列的同一事件顺序中完成“登记订阅者并返回当前快照”。每个更新携带任务标识、状态版本和不可变快照；页面只接受新于自身所见版本的通知，从而避免订阅窗口漏更新、异步通知乱序或旧错误覆盖新状态。

列表与详情通过同一任务标识定位记录。UI 可以有按钮提交中的局部状态，但不得自行预测并写入成功、失败或已取消等权威任务状态。页面卸载仅解除订阅；重新进入时取最新快照。一个页面发出的取消、重试或继续操作，经队列接受后向所有订阅者广播。应覆盖订阅期间终态到达、详情卸载后取消回调、重复挂载不重复订阅等路径。

## 生命周期、兼容与数据边界

API、权限范围、本地文件格式保持既有契约。新增信息仅存于进程内，不新增数据库、Schema、任务恢复文件或 Secret。任务只保存文件引用，日志使用任务标识、尝试序号、状态变化与必要错误类别，避免记录令牌和原文件正文。

应用退出时可对在途请求执行尽力取消，但不能把它当作远端撤销保证。重启创建新的队列实例标识，旧任务及旧回调不恢复；现有本地文件列表与详情仍读取原有数据。跨重启幂等性不扩展为持久化承诺。

## 失败恢复与可撤回路径

| 失败模式 | 处理与用户恢复 | 需要验证的恢复点 |
|---|---|---|
| 网络 / 服务端失败 | 记录失败，等待手动重试；保留任务键和原文件 | 同键不会重复创建远端资源 |
| 取消响应迟滞或失败 | 维持已取消，拒绝迟到回写；未结束请求继续占名额 | 请求结束后只释放一次名额 |
| 令牌过期 | 全局暂停，登录后由用户手动继续 | 暂停期间无新增上传、原文件保留 |
| 订阅中断或重挂载 | 新订阅获取当前快照，按版本跟随 | 不重建任务，不追加上传 |
| 集成引起本地页面回归 | 撤回新增上传入口、订阅接线和队列启动，恢复原本地列表 / 详情路径 | 实施前记录的本地行为与原文件读取 |
| 应用重启 | 不恢复旧队列，不自动发起请求 | 原文件内容和原有路径可用 |

当前没有已验证的完整上传稳定提交，不能给出虚构回滚哈希。开始实施前须记录本地列表、详情和原文件的可恢复基线；每个小切片保留差异与验证记录。恢复不删除本地文件，也不调用未获授权的远端资源清理接口。

## 已知限制

服务端是否立即回收取消任务的带宽未知；本方案通过本地终态保护和保守名额计数约束行为，不能承诺远端即时释放或撤销已创建的资源。适配层若无法给出可靠的请求结束信号，需先调查并调整内部方案，不能盲目扩大并发。
