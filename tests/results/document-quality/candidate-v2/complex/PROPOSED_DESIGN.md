# 方案设计 — R3 后台上传

建议在页面生命周期之外新增一个应用级内存后台队列，统一管理状态、调度和广播，并复用现有 API 适配层。取消先封住本地状态再请求取消传输；重试复用幂等键并隔离旧响应；列表与详情只订阅队列快照。这些措施分别控制取消竞态、重复远端资源和跨页面状态分叉。

## 方案状态与约束

- Status: `PROPOSED`；目标 Release：R3。本文是尚未实现的技术方案，不能作为当前已集成架构引用。
- 依据：[需求分析](SPEC.md) 的 REQ-001～REQ-006；[INPUT.json](INPUT.json) 的 `chosen_direction`、`current_architecture`、`approved_contract` 与 `recovery`。
- 用户已确认后台队列唯一写入、双页面共用订阅、复用现有 API 的方向及外部边界；下文细化内部执行顺序，不新增产品范围或重复申请既有批准。
- 当前仅有本地文件列表和详情页，尚无正式后台队列。隔离探针及其 E-02 记录的覆盖限制见 [进度“证据边界”](PROGRESS.md#证据边界)。

## 组件职责与选择理由

| 目标组件 | 唯一职责 | 设计理由 |
|---|---|---|
| 应用级内存队列 | 接收创建、取消、重试、继续及 API 事件；串行写入任务状态；调度最多 2 个传输；发布快照 | 状态与调度共用一个写入入口，便于判定事件先后并维持并发上限 |
| 既有 API 适配层 | 携带幂等键、发起上传、传递取消与鉴权错误；向队列返回结果 | 保留既有外部契约，避免再造上传 API |
| 共用订阅入口 | 为两个页面提供当前快照及后续状态版本 | 页面重入直接获得最新状态，避免靠历史事件补状态 |
| 列表页与详情页 | 读取同一任务、发送用户操作意图、展示状态及登录提示 | 页面挂载和卸载不创建、销毁或直接推进任务 |

既定方向适合当前限制：无需持久化或新增服务即可消除页面各自持有上传任务造成的状态分叉。分别在页面内维护队列会让切页、取消和迟到响应跨越多个写入者，违背 REQ-004；本方案不采用该路径。

## 调度与状态唯一写入

队列在应用进程内创建一次，页面通过同一入口取得它。任务只保存本次会话需要的任务标识、创建序号、本地文件引用、状态、幂等键和尝试代次；不建立持久化存储，也不更改本地文件。

创建时分配稳定任务标识与幂等键。用户手动重试仍是同一任务，保留创建序号和幂等键；内部调度按原任务创建顺序挑选可执行的排队项。失败、成功和已取消任务不参与调度，暂停条件未解除时不启动任何新上传。

所有命令与回调经过队列的同一串行状态转换入口。一次有效转换先提交完整状态快照，再广播递增版本；页面不能跳过该入口写状态。重复的取消、继续或完成事件按当前状态处理，不能重复启动请求、重复释放并发位或产生倒退版本。

并发位由实际在途的上传尝试占用，而不是简单统计页面显示的“上传中”任务。取消后任务可以立即显示已取消，但对应传输在原上传请求结束或传输层确认停止前仍占位；仅收到“取消命令已接受”不能释放并发位。结束事件只释放一次。这样不会在旧传输仍在途时启动第三个请求。若取消完成迟迟得不到确认，队列可能等待空位；必须在集成时验证适配层的取消完成语义，不能以提前释放并发位掩盖该问题。

## 取消、失败与旧响应隔离

### 取消的先后关系

1. 队列接收取消命令，确认任务仍处于排队或上传中；先把任务写为已取消并广播。
2. 排队任务退出可调度集合；上传中任务向既有适配层发出取消请求。取消传输的完成与本地取消状态分开记录。
3. 所有后续回调在写入前核对任务标识、尝试代次与当前状态；已取消任务拒绝成功或失败覆盖。即使取消请求失败，任务也不能被迟到成功恢复。
4. 若有效成功事件已经先于取消命令提交，任务已经成功，后到的取消不能被报告为一次成功的“上传中取消”。测试须覆盖这两个事件顺序。

本地已取消不证明服务端没有处理上传，也不证明带宽已立即回收。方案不新增远端删除或补偿 API；对取消后的远端资源即时回收不作承诺。

### 失败与手动重试

普通失败将当前任务置为失败，不注册定时重试，也不因页面挂载或网络恢复自动重试。用户重试时，队列确认任务为失败，再把它重新排队并增加尝试代次；原幂等键不变。

每个 API 回调都绑定发起时的尝试代次。前一次尝试迟到的成功或失败，不得改写新尝试的状态；其传输结束信息仍需完成旧并发位的单次清理。对网络中断后远端已经成功、客户端却记为失败的情况，同一幂等键是再次请求时防止重复资源的边界。该边界须通过真实适配集成核对，不能由客户端单测替代。

## 令牌过期与手动继续

队列增加一个独立于任务终态的调度条件：正常、等待登录、等待手动继续。它不是新的失败重试机制。

- 收到有效的令牌过期事件后，先关闭调度入口，再暂停未完成上传。对在途尝试请求取消，隔离其后续状态回调，将被中断的任务保留为受暂停条件约束的排队任务；旧传输仍按实际结束情况释放并发位。
- 尚未启动的任务保留创建顺序，暂停期间展示“已暂停/请登录”的原因。已有成功、已取消或普通失败任务保留原状态。
- 登录成功只把调度条件转为等待手动继续。队列只有接收用户继续命令、且登录条件有效时才重新调度；再次令牌过期时重新关闭入口。
- 继续被中断的同一任务仍复用其幂等键，并增加尝试代次；普通失败任务必须另由用户手动重试。“继续”不能遍历并重启所有终态任务。

这使登录状态变化与上传启动分离，同时复用取消及旧响应隔离机制。两处页面显示的暂停原因也来自同一队列快照。

## 列表与详情的传播和重入

订阅入口应在同一串行边界内完成“登记订阅并取得当前快照”，避免读取快照与订阅之间丢失一次状态更新。页面按递增版本接收完整快照或从同一快照派生的视图，忽略过期通知。详情用稳定任务标识读取对应任务，不能在页面加载时重新创建上传。

页面卸载只解除该页面的监听，不取消任务或销毁队列。页面重新进入时读取当前快照，因此能看到离开期间发生的取消、失败或成功。两个页面的取消、重试和继续按钮都发给队列处理，成功与错误显示均由下一份队列快照决定。

应用重启后重新建立空内存队列；不读回旧任务或根据本地文件自动重建上传。本地文件列表与详情仍沿用既有读取路径。

## 影响、风险与恢复

受影响范围包括新增队列与订阅入口、既有上传适配层的接线、列表和详情的任务状态展示，以及登录事件到队列的通知。API、权限范围、本地文件格式保持已确认契约；尚未读取真实代码，不能据此声称这些模块已经核查无影响。具体文件路径与现有工程接入方式应在后续实现前定位。

主要风险是取消完成语义不清导致并发位滞留、旧响应污染新尝试、订阅重入丢事件，以及登录成功触发隐式恢复。前述状态边界和下表检查用于验证这些风险，当前没有集成证明。

恢复按以下顺序准备：停止新增任务和调度 → 隔离回调并请求取消在途传输 → 撤回新增队列/页面接线 → 恢复既有本地列表与详情路径 → 验证全部本地原文件仍可读取。没有已验证的完整上传稳定提交，不能填写或承诺可回退到某个上传版本。撤回客户端接线也不等于撤回已发生的远端上传；服务端即时回收仍属已知未知项。
