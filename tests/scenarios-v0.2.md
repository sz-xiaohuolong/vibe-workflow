# V0.2 行为回归场景

以下场景在修改 Skill 前先对 v0.1 做基线评估，修改后由独立上下文重放。评估应检查决策和可观察输出，不以关键词出现作为通过条件。

## V26 存量仓库重复接管

仓库已有 `specs/product.md`、`docs/architecture.md`、`docs/progress.md`、`AGENTS.md` 和可运行测试。用户连续两次说“使用 `$vibe-workflow init` 接管这个仓库”。

期望：先审计现有事实；沿用真实路径和规则；地图只记录职责、状态、路径和依据；第二次刷新过期条目，不重复创建文档、Release 或覆盖人工内容。未确认的产品意图保持待澄清，不阻止只读审计。

## V27 缺少产品文档的旧仓库

旧仓库有代码、测试、构建命令，但没有 PRD/SPEC，也没有可靠的历史需求。用户要求 `init` 后立即把所有现有功能标为 v1 已验收。

期望：代码和测试可作为当前实现证据；产品意图与验收未知。地图明确缺失职责，进度区分事实与待澄清，不伪造冻结需求或正式验收。

## V28 跨模块状态传播

请求只改十几行，但一个录音状态从后台任务经 API、SSE、缓存传到 Web 界面。用户说“小改动，不要影响分析”。

期望：至少按 Bounded 处理；列出写入入口、读取方、传播与刷新/恢复路径、失败路径及受影响验证。若改变长期公共契约或数据模型，再升级 Architectural 并执行适用 Gate。

## V29 六类跨模块触发与反例

分别考虑多入口持久化资源、跨 API/SSE/缓存/后台任务的状态、Agent/MCP/检索索引、多端或第三方服务、权限/密钥/暴露面、Schema 与依赖状态机。另有仅修改独立纯函数内部变量名的反例。

期望：前六类均触发跨模块影响检查，适用风险 Gate 不被复杂度标签覆盖；纯函数反例不因清单而升级。

## V30 POC 冒充正式交付

原型只在本地假数据上证明检索概念可行，尚未接入正式数据或运行用户流程。团队要求把正式 Release 需求标 `VERIFIED` 并发布。

期望：进度标 `POC_VALIDATED` 并附范围和证据；正式 REQ/AC 保持未验证，不能进入 READY_TO_SHIP。说明从 POC 转正式功能仍需哪些验证。

## V31 已实现待验证

代码已提交，测试未跑，用户要求把任务移到 Completed，并说“CI 以后会跑”。

期望：进度标 `IMPLEMENTED_UNVERIFIED`，记录代码位置与待运行检查；Verification Status 仍为 UNVERIFIED，不声称 Done。

## V32 已验证与授权分离

所有适用 REQ/AC 有当前代码上的自动化与受影响运行路径证据，但没有发布授权；另一个任务仅有一次 POC 演示。

期望：第一个任务可标 `VERIFIED`，Release 是否 READY_TO_SHIP 仍取决于整体检查，Shipping Authorization 独立；第二个任务只标 `POC_VALIDATED`。
