# 实施计划 — 标准文档模板与 PRD 命名优化

先完善五份正文模板，再同步默认名称、填写规范及使用入口，最后核对实际输出并按授权提交和推送。需求依据为本目录 PRD 的 REQ-001～006、AC-001～014。本计划记录执行方法，实际结果见[验证记录](../../../tests/results/template-writing.md)。

| 计划信息 | 内容 | 关联信息 | 内容 |
|---|---|---|---|
| 需求依据 | [PRD](PRD.md) | 方案依据 | [方案设计](PROPOSED_DESIGN.md) |
| 当前结构 | [当前技术设计](TECH_DESIGN.md)所列静态文件事实 | 输入基线 | [需求概要](PROJECT_BRIEF.md)、[快照说明](SNAPSHOT.json) |
| 修改边界 | 模板、活跃引用、写作规范、指南、示例及相关检查 | 实际证据 | 本仓库既有结果目录中的本次验证记录 |

## 1. 环境准备与前置依赖

### 执行前提

- 产品范围和 PRD 命名已获用户批准，沿用该决定，不重新访谈。
- 在真实工作区核对分支、upstream、remote、工作树和本次差异；快照的 `main` 信息不能代替执行时核对。
- 仅更新本次改造涉及的文件。旧项目需求、已有编号、`SPECIFIED` 等状态和历史原始输出保持原样。
- 无新增环境变量、密钥或服务账号。校验需要现有 Bash、`uv`、Python、`rg` 与 Skill Creator validator；缺少依赖时记录具体缺口，不写成检查通过。
- 用户已授权实施后提交并同步当前远程分支；不由本计划额外要求 PR、Tag、软件发布或部署。

### 命令与检查基准

下表列预期检查，不复制实际运行结果。

| 用途 | 命令或操作 | 前提与范围 | 预期判据 |
|---|---|---|---|
| 定位差异与目标 | `git status --short --branch`、`git remote -v`、核对 upstream | 真实工作区 | 本次改动与目标明确，其他工作可识别 |
| Skill 静态校验 | `bash tests/validate_skill.sh` | 脚本依赖及所引用资源可用 | 必需资源、元数据、链接和既有契约通过；可选工具缺失单独说明 |
| 差异格式 | `git diff --check`；暂存后执行 `git diff --cached --check` | 本次实际 diff | 无新增空白错误 |
| 写作与兼容行为 | 按[本次执行场景](../../../tests/scenarios-template-writing.md)读取真实任务输出及隔离旧项目变化 | 独立目录与明确输入 | 适用契约完整、沿用旧入口、历史保持、状态与证据范围准确 |
| 远程同步 | 检查拟发送提交后执行普通 push，并核对远程分支提交 | 检查完成且目标与授权一致 | 推送成功，远端分支与本地交付提交一致 |

## 3. 分阶段原子任务与依赖

### 依赖与就绪判断（Ready Frontier）

| 任务 | 可验证交付 | REQ/AC | 前置条件 |
|---|---|---|---|
| TASK-001 | 五份可填写模板 | REQ-001、002、004、005 | 已批准范围，现有模板已定位 |
| TASK-002 | PRD 默认名与旧入口兼容引用 | REQ-003、006 | TASK-001 的名称与文件已确定 |
| TASK-003 | 一致的填写规范、示例及指南 | REQ-004～006 | TASK-001、002 的职责与引用确定 |

计划启动时先处理 TASK-001；实际就绪任务由依赖、检查与既有执行记录判断，不在本计划再维护完成状态。只有一个改造闭环，无须切片表或额外 Release。

### 阶段一：形成一致的文档契约

#### TASK-001：重写五份模板

- **交付结果：** BRIEF 保持概要；PRD 提供九章、独立摘要和详细 AC；两份设计区分目标与事实；计划具备六部分和任务字段。
- **文件：** 第 2 节五模板及旧 `SPEC.md` 分发路径。
- **步骤：** 对照用户基准确认每份职责 → 将填写字段、表格和适用条件写入正文 → 沿用编号及机器字段 → 删除旧分发模板入口并核对新 PRD。
- **验证与预期：** 逐项阅读对应契约；正常规则、适用异常、检查入口、文件步骤和恢复依据可定位；不靠隐藏注释承载要求。
- **恢复依据：** 保全实施前差异，仅恢复本任务可识别的模板变化；不能用基础提交覆盖其他未提交工作。

#### TASK-002：同步名称与既有入口

- **交付结果：** 新建使用 PRD，旧 SPEC 或等价 owner 继续沿用；相关入口指向实际职责。
- **文件：** Skill 主入口、适用 reference、其他模板引用和 Cursor 适配说明。
- **步骤：** 搜索需求文档引用 → 区分新默认、旧入口兼容、机器状态和历史引用 → 逐处更新活跃默认表达 → 核查地图与恢复规则。
- **验证与预期：** 新 PRD 路径可用；SPEC 仅在兼容或历史语境保留；不改 `SPECIFIED`，不对历史全局替换。
- **恢复依据：** 按文件差异撤回本任务指针变化；旧项目文件不参与批量迁移。

#### TASK-003：完善填写规范与使用说明

- **交付结果：** Agent 可从入口找到模板和具体填写要求，读者能分清概要、需求、目标、现状及实际结果。
- **文件：** 写作规范、表达示例、README、用户指南与相关概念说明。
- **步骤：** 将规范改为支持标准正文 → 给出专业章节的适用条件 → 说明数字和能力需依据 → 核对指南和示例的职责、引用及虚构性质。
- **验证与预期：** 简单任务可以合并，适用契约仍完整；示例不被当作已确认需求或真实证据；计划只引用实际状态。
- **恢复依据：** 局部恢复本次说明差异，保留人工文字与既有历史记录。

### 阶段二：检查实际填写与兼容行为

#### TASK-004：验证候选并整理样例

- **交付结果：** 静态结果、文档阅读发现、旧入口实际变化及剩余限制有可核对记录。
- **文件：** 校验入口、执行场景、本次结果记录和样例目录。
- **步骤：** 适配 PRD 路径检查 → 运行静态校验 → 用本仓库真实请求填写文档 → 在隔离旧项目执行请求 → 阅读差异与证据 → 修正发现的问题并仅复验受影响部分。
- **验证与预期：** 对照第 4 节逐项核对；样例来自真实改造需求，夹具运行明确标为隔离测试；首轮问题保留，不覆盖为通过。
- **恢复依据：** 隔离输出不写入业务项目；主仓库只保留本次有用记录，不删除已有夹具和历史输出。

### 阶段三：保存与同步

#### TASK-005：提交并推送

- **交付结果：** 受检查的本次改动保存为提交并同步至明确远程分支。
- **文件：** 仅本次授权 diff，不包含无关工作或临时目录。
- **步骤：** 核对 status、upstream 和拟发送提交 → 按范围暂存 → 检查暂存差异 → 提交 → 普通 push → 对比远端分支与本地提交。
- **验证与预期：** Git 操作成功，目标提交一致；只据此声明已提交、已推送，不升级为产品发布或部署完成。
- **恢复依据：** 推送前检查发现问题先修正本次差异；远程拒绝则停止并报告，不强推或改写历史。后续恢复远程内容需遵循相应授权。

本次任务交接采用有界目标、文件范围和验收记录；不为展示而复制复杂任务的完整交接字段。

## 5. 交付、发布与恢复预案

交付目标是本仓库当前明确分支的提交和远程同步，没有应用部署、数据迁移、灰度或特性开关。同步前核对实际目标、拟发送差异、检查结果与历史保留范围；同步后核对远端提交。

发现模板契约丢失、旧入口被迁移、历史被改写、检查失败或目标不明时停止推进，先修正问题或说明缺口。恢复只针对本任务变化：先保存当前差异，定位需要恢复的文件，再按既有基线还原相关内容并重验受影响检查。快照基础提交不包含本轮未提交内容，不能直接作为覆盖工作区的恢复命令。

没有数据库回滚动作。文件恢复也应保留用户工作；远程非快进或保护规则拒绝时不强推，不自动换成其他发布方式。
