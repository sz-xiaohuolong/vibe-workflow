# 标准文档模板与 PRD 命名优化需求概要

本次为 `vibe-workflow` 提供可直接填写的五类工程文档模板，并统一新建产品需求文档的 PRD 名称。模板应帮助 Agent 写出可以理解、实施和验收的正文，同时保留存量项目入口、需求编号、机器状态和历史记录。详细规则见[产品需求文档](PRD.md)，技术现状见[当前技术设计](TECH_DESIGN.md)。

## 需求控制（Requirement Control）

- Requirement Version：`TW-01`，对应本次外部提供的 `TW-01-input.md` 任务基线，不代表软件发布版本。
- Requirement Status：`FROZEN`，仅表示任务输入列明的产品范围已经用户批准，不表示实现或验证完成。
- Approved By：用户；依据为任务输入中的“用户已批准以下范围”。
- Approved At：任务输入未提供具体批准时间，不以快照日期代替。
- 关联 PRD：[PRD.md](PRD.md)。
- 范围依据日期：2026-10-20；仓库版本事实见[快照元数据](SNAPSHOT.json)。本次未指定正式 Release ID，因此不建立发布版本或迁移完整生命周期状态。

## 1. 背景与产品定位

**现状与痛点。** Vibe Workflow 通过 Skill、参考规范和模板指导 Agent 跨会话协作。只告诉 Agent “写清需求”“描述架构”仍不足以约束具体正文：需求可能退化为几行摘要，方案可能混入未核验的现状，任务可能缺少文件、验证和恢复依据。新建与存量项目使用不同的需求文件名时，还容易产生第二份需求 owner 或破坏既有引用。

**事实依据。** 本次任务明确要求五份可填写模板、PRD 九章及旧 SPEC 兼容。[Skill 主入口](../../../skills/vibe-workflow/SKILL.md)已声明写作前读取模板；[文档写作规范](../../../skills/vibe-workflow/references/document-quality.md)已规定职责及填写要求；快照中已经包含五模板及相关引用。本次据实际文件描述当前内容，但没有运行检查，也没有读取以往生成输出或借用其中结论。

**产品定位。** 本次交付是 Skill 内部的文档写作契约：模板提供稳定骨架，reference 解释适用条件，指南与示例帮助读者使用，校验保护公开结构。它不增加业务应用、在线文档平台或新的运行服务。

## 2. 目标用户与核心场景

| 目标用户 | 使用环境与权限边界 | 核心诉求 | 触发场景与成功结果 |
|---|---|---|---|
| 使用 Vibe Workflow 的 Agent | 在用户已授权的项目目录中读取 Skill 和项目事实；遵守项目原有入口与权限 | 直接按模板填写，知道需要展开什么、引用什么、哪些事实不能猜 | 新建或实质修改核心文档时，形成可实施、可验收且无虚构事实的正文 |
| 开发者、项目负责人或需求确认者 | 阅读项目需求、设计及计划，决定产品承诺和重大风险 | 单独阅读 PRD 即可理解目标和用户，通过引用追溯概要及依据 | 审阅文档时能判断范围、方案理由、当前事实及后续任务 |
| Skill 维护者 | 维护本仓库活跃入口、模板、指南、示例和静态校验 | 一处契约变化能同步到所有适用活跃入口，历史输出保持原貌 | 调整命名和写作规范后，新项目用 PRD，旧项目仍可恢复原需求文件 |

**核心流程概要：** Agent 确认既有范围与事实 owner → 读取对应模板及填写要求 → 按真实项目填写正文并精确引用 → 用适用检查核对结构与兼容 → 由既有进度和验证记录维护实际结果。简单任务继续采用现有裁剪规则，不因五模板齐备而强制生成五份文档。

## 3. 目标与范围

### 核心目标

- 让 Agent 能直接填写需求概要、PRD、方案设计、当前技术设计和实施计划；正文包含该文档承担的可执行信息。
- 让 PRD 按统一九章展开，前三章先有独立摘要，再引用概要的相应章节。
- 让新建需求文件默认使用 PRD，存量 SPEC 和等价入口继续作为唯一需求 owner。
- 让目标、现状、预期任务和实际证据各有归属，避免把计划或授权写成验证通过。
- 让专业内容以适用条件展开，避免模板诱导新增产品能力或套用示例数字。

### 本次范围

- 五模板的正文骨架、填写字段、示例占位和职责提示。
- Skill 主入口、文档治理和写作 reference、活跃模板间引用、用户指南、README、Cursor 适配入口及相关校验的同步。
- 五份文档之间的 GOAL → REQ/AC → 设计 → Task → 计划验证入口追溯。
- 原始任务中的提交与当前远程分支同步交付方式；本次只读快照写作仅把它记入计划。

### 非目标

- 不重命名、迁移或复制存量项目的 SPEC，不重写封存历史。
- 不更改既有 REQ/AC、Task 编号、`SPECIFIED` 等机器状态或七阶段模型。
- 不新增数据库、缓存、服务接口、自动重试、特性开关、埋点平台或文档生成程序。
- 不因模板完善而自动初始化项目、建立第二套地图或要求每篇文档单独批准。
- 本次写作不修改 Skill 源文件，不安装、不联网、不执行检查、不提交、不推送、不发布。

## 4. 总体约束

| 约束维度 | 已确认要求 | 来源与影响 |
|---|---|---|
| 默认命名与兼容 | 新建用 `PRD.md`；旧 `SPEC.md` 或等价路径沿用，不复制第二份 | 已批准范围；影响主入口、地图、模板、恢复和指南的表达 |
| 职责分工 | 概要拥有意图基线；PRD 拥有行为与 AC；方案拥有目标与理由；当前技术设计拥有已核验事实；计划拥有预期任务 | 已批准范围与文档治理规范；不重复维护实际状态 |
| 写作语言 | 正文使用简体中文；文件名、字段名和机器状态按既有契约保留 | 当前任务与项目语言规则 |
| 事实和证据 | 文件存在可作为静态事实；检查是否执行及结果必须另有真实证据 | 快照元数据注明不包含本轮运行结果；不能从源码推断通过 |
| 裁剪与成本 | 适用契约必须展开；不适用内容说明原因或省略；数字须有依据 | 已批准范围；没有性能、容量、覆盖率或工期数值承诺 |
| 本次写入边界 | 只在本目录生成五份指定文档，其余快照只读 | 当前任务明确限制，优先于原始任务的提交推送授权 |

## 5. 成功指标与验收目标（Acceptance Goals）

本次没有已测量的效率或质量基线，因此以可判定的行为目标衡量价值，不承诺提升比例。下表是目标，未记录实际通过结果。

| 目标编号 | 可观察目标 | 判定口径与依据 | 验证方式 |
|---|---|---|---|
| GOAL-001 | 五模板可直接指导正文填写 | 读者能找到各自适用章节、字段、契约及不适用处理；不是仅有标题或提示语 | 后续逐模板静态审阅，并以本仓库真实任务审阅可填写性 |
| GOAL-002 | PRD 独立可读且可验收 | 九章齐备；背景、目标、用户各有摘要并精确引用概要；功能具备前提、规则、异常和可观察 AC | 对照 PRD 模板和写作要求逐项审阅 |
| GOAL-003 | 新旧命名兼容且历史不变 | 新入口指向 PRD；既有 SPEC 路径、REQ/AC 和机器状态不被改写 | 后续核对活跃引用与拟提交差异，观察新建与存量两条路径 |
| GOAL-004 | 五文档事实职责清晰 | 方案说明目标与理由，当前技术设计可定位事实依据，任务可执行，结果归属进度/验证记录 | 交叉审阅需求、设计、计划与实际文件，证据缺口保持可见 |
| GOAL-005 | 完成交付入口同步 | 活跃引用、指南、示例及适用校验反映同一契约，历史输出不改 | 后续静态校验、引用审阅和范围差异核对；全部尚未由本次执行 |
