# 工程文档写作规范

## 何时读取

新建或实质修改 `SPEC`、`PROPOSED_DESIGN`、`IMPLEMENTATION_PLAN`、`PROGRESS` 时读取本文件的通用规则与对应类型。小更新只读取相关段落；普通 Git、未产生文档变化的任务不额外加载。示例按需要查阅[正例与反例](../assets/examples/document-quality.md)。

事实所有权、历史封存与同步职责由 [artifacts.md](artifacts.md)维护，是否需要文档由 [routing.md](routing.md)决定。本规范是写作步骤的一部分，不增加阶段、审批或专业技能调用链。

## 通用写法

默认读者是正在 vibe coding、需要理解和判断方案的用户。先说明结果及其影响，再提供足够实施和验收的细节。

1. **开头给答案。** 标题使用“需求分析”“方案设计”“实施计划”“进度”。首段或短摘要说明用途与核心结论，并指出适用的风险、未决事项、验收或下一步入口。沿用既有文件名、编号和机器状态值。
2. **一段回答一个问题。** 用具体主语、动作和结果写短句；直接写结论与理由。必要术语首次结合项目解释，同一概念保持同一称呼。
3. **按信息选择形式。** 步骤用编号列表，并列事项用列表，同维度比较用表格；只有顺序、分支、状态或组件关系难以用短文讲清时才画图。标题逐级组织并描述内容。
4. **正文服务判断。** 先写目标、选择理由、关键边界和影响；函数清单、完整日志等只在确实影响实现或验收时展开。已有细节用精确章节、REQ/AC、Task 或证据入口引用。
5. **一个事实一处明细。** 摘要负责定位，正文负责展开；其他文档引用事实 owner。使用同一文件内分层满足阅读需要，内容有独立职责且会独立维护时再拆文件。
6. **诚实呈现状态。** 区分当前事实、目标方案、假设和未知。失败、风险、阻塞及未验证事项在摘要或对应状态处可见；证据只支持实际覆盖范围。可查事实自行核验，查不到的明确标注。

## 四类文档的最小结构

| 文件与名称 | 必答问题 | 最小正文 |
|---|---|---|
| `SPEC`：需求分析 | 做什么，边界是什么，怎样算完成？ | 范围摘要 → 需求基线 → REQ 与可观察 AC → 验收入口 |
| `PROPOSED_DESIGN`：方案设计 | 用什么方案，为什么，影响和风险是什么？ | 推荐方案摘要 → 方案状态与约束 → 设计与理由 → 适用影响、风险和恢复 → 验证方式 |
| `IMPLEMENTATION_PLAN`：实施计划 | 先做什么，依赖什么，如何证明完成？ | 目标与依据 → 有交付结果的任务及依赖 → 修改边界、验证与恢复依据 |
| `PROGRESS`：进度 | 到哪了，缺什么，下一步做什么？ | 当前事实/缺口/下一步摘要 → 必要定位 → 适用的任务与证据明细 |

范围、边界、风险和恢复等必要事实可合并成短段或精确引用，不必各占一个章节。继承既有等价结构时按语义应用，不重命名历史路径或重新编号已确认条目。

## 按条件展开

### 需求分析

- **单一同步交互：** REQ、AC 和适用错误/边界即可。同一输入到结果的简单派生不另写流程图或状态表。
- **先后顺序影响结果的多步骤操作：** 补用户流程，重点标出顺序、分支和失败恢复；引用 AC，不重述整套行为。
- **存在独立生命周期、异步事件或转换限制：** 补状态转换，明确事件、条件和可见结果；取消、重试等竞态也写在此处。
- **跨模块/系统验收或观察位置不明显：** 补测试接缝，即从哪里输入、观察什么输出或状态。简单行为可在 AC 旁直接写检查入口，无需独立索引再复制一遍。

错误、输入边界和非目标根据已知事实写入相关 REQ 或范围段。未知事实保留为未知，不为补齐模板编造需求。

每项 AC 追溯到已确认行为；验收示例只实例化已有规则。缺少且会改变用户可见结果的条件标为待澄清，并说明受影响的验收范围；输入标为已冻结也不授权补充产品含义。普通内部实现选择写在方案设计中，不反向变成新需求。

### 方案设计

- **已有当前架构：** 精确引用其相关事实，再写本次改变；目标结构明确标注方案状态。
- **存在实质备选：** 比较选择理由与代价，不为凑数量编造选项。
- **涉及接口、数据、权限、兼容或迁移：** 展开对应契约、风险、所需决定及恢复方式。无此影响时，一句边界说明即可。
- **跨模块共享状态：** 保留写入入口、读取方、传播/刷新/恢复、失败与取消路径及受影响、已核查未受影响的模块。未核查不能写成已确认无影响。

已有授权继续使用；方案状态与实现状态独立。“方案设计”这个名称不表示已批准或已实现。

### 实施计划

默认用任务表写清交付、REQ/AC、依赖、修改边界、验证与恢复依据，状态明细由既有进度记录维护。共同约束写一次，任务引用差异。

- **任务有依赖：** 标出顺序与当前就绪任务（Ready Frontier）；前置条件可直接从表格判断时不另画拓扑。
- **多个业务闭环：** 增加切片映射；只有一个闭环时不机械建立切片层级。
- **真正委派复杂任务：** 在执行前按 [Task Handoff Contract](execution.md#task-handoff-contract-统一任务派发契约)组装完整上下文、范围、风险、证据和恢复点。计划保留定位引用；简化展示不免除交接事实核对。

### 进度

标题后最多三条数据行的摘要用于回答当前事实、缺口和下一步。摘要引用下方对应记录，不复述全部任务或证据。

- **只有一个任务：** 一段当前记录可承载状态、证据和下一步，省略任务表与切片表。
- **多个任务：** 用一张任务表维护状态，验证结论在对应任务行链接证据；需要统一解释证据覆盖时再增加证据明细。
- **确有切片或熔断：** 分别增加切片清单或 Debug Snapshot，其他情况不预置空记录。

## 写完与修改时检查

先确认本次需要改变的事实，再写作并直接修复表达问题。

- **小更新：** 检查改动部分、受影响引用及必要的相邻上下文；保留无关段落、人工说明和历史事实。
- **重要新建或实质修改：** 检查整体用途和顺序；读者能否找到结论、边界、风险及适用的验收或下一步；是否存在重复视图、空章节、模板占位符、无依据事实或过多跳转。
- **工程契约：** 裁剪后仍保留所有适用需求与 AC、风险决定、证据、依赖、交接和恢复信息，状态不因文风改变。发现范围或取舍问题时沿用已有 Gate；文风问题自行修正。

先保证准确完整，再改善理解、删除冗余并统一形式。字数、章节数和格式检查仅作辅助；已有文档随任务渐进整理。
