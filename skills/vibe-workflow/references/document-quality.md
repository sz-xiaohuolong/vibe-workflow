# 工程文档写作规范

## 何时读取

新建或实质修改需求概要、PRD、方案设计、当前技术设计、实施计划、进度或 API 调用文档时，先读下表对应模板，再读本规范的通用写法和对应部分。小更新只读相关内容；普通 Git、未产生文档变化的任务不额外加载。表达示例见[正例与反例](../assets/examples/document-quality.md)。

事实所有权、历史封存与同步职责见 [artifacts.md](artifacts.md)，是否需要文档由 [routing.md](routing.md)决定。本规范用于改善写作，不新增审批或阶段。

## 模板与职责

| 文档 | 模板 | 应交代的内容 |
|---|---|---|
| 需求概要 | [PROJECT_BRIEF.md](../assets/templates/PROJECT_BRIEF.md) | 问题、定位、用户、目标与非目标、总体约束、成功指标和确认基线 |
| 产品需求文档（PRD） | [PRD.md](../assets/templates/PRD.md) | 背景、目标、用户、功能优先级、详细行为与验收、交互状态、约束边界、埋点、待决问题 |
| 方案设计 | [PROPOSED_DESIGN.md](../assets/templates/PROPOSED_DESIGN.md) | 技术目标、栈与工程约定、架构及数据流、详细契约、取舍、安全观测、风险与恢复验证 |
| 当前技术设计 | [TECH_DESIGN.md](../assets/templates/TECH_DESIGN.md) | 已实现且经核验的架构、接口、数据、运行及验证入口，以及相应事实依据 |
| API 调用文档（按需） | [API.md](../assets/templates/API.md) | 调用方的接入、认证、参数约束、成功与失败示例、适用版本和兼容限制；沿用既有契约源 |
| 实施计划 | [IMPLEMENTATION_PLAN.md](../assets/templates/IMPLEMENTATION_PLAN.md) | 前置依赖、文件映射、阶段任务、验收追溯、发布恢复预案、里程碑与偏差入口 |
| 进度 | [PROGRESS.md](../assets/templates/PROGRESS.md) | 当前事实、验证缺口、任务状态、证据和下一步 |

新建需求文件使用 `PRD.md`。已有 `SPEC.md` 或等价路径继续沿用并作为 PRD 读取，不迁移、不另建一份；既有 REQ/AC、Task 编号与 `SPECIFIED` 等机器状态不变。

## 通用写法

默认读者是正在 vibe coding、需要理解和判断方案的用户。标准模板决定正文结构，简洁体现在删除重复和无关内容，不能省略实施与验收所需的信息。

1. **开头说明用途和结论。** 使用明确中文名称，简述范围、推荐方案或当前事实；相关风险和未知应直接可见。元数据只保留实际用于定位、确认或维护的字段，不编造负责人、日期、版本与评审结论。
2. **一段回答一个问题。** 用具体主语、动作和结果写短句；先给结论，再给理由。必要术语首次结合项目解释，同一概念保持同一称呼。
3. **按信息选择形式。** 步骤用编号列表，同维度信息用表格。只有顺序、分支、状态或组件关系难以用短文讲清时才画图；图表与文字各承担不同信息，不重复表达全部内容。
4. **正文提供可执行细节。** 功能写流程、规则与异常，设计写字段、接口和选择理由，任务写文件、步骤与验证预期。不能用“按需实现”“完善错误处理”等空话代替契约，也不能只在 HTML 注释中保留填写要求。
5. **摘要可独立理解，明细只有一个 owner。** PRD 开头用短文概述背景、目标和用户，再链接 BRIEF 相关章节。其他位置用精确章节、REQ/AC、Task 和证据入口引用；不要复制完整背景、另一份任务状态表或日志。
6. **事实与设想分开。** 区分当前事实、目标、假设和未知。可查事实自行核验；查不到的标明待确认或未核验及影响。计划、批准、POC 和代码存在都不等于运行验证通过。

## 结构裁剪与适用条件

- **常规功能使用标准章节。** 先判断每章是否适用，再填写；不要默认退化为几个摘要字段。需求、方案和任务中的适用契约必须完整。
- **简单任务允许合并。** 背景、目标与用户可写成几段短文；单一任务可用一张表承载交付、文件、步骤和验证。合并后仍应能直接找到所有适用信息。
- **专业章节按影响展开。** 无界面不写页面状态，无持久化变更不造表结构，无埋点需求不新增采集。会影响读者判断的省略给出一句“不适用及原因”，不保留空表或逐项堆砌“无”。
- **例子不是默认需求。** 性能、容量、覆盖率、工期、告警阈值和灰度比例有已确认依据才填数值；不默认引入数据库、缓存、重试、特性开关、额外依赖或 Commit/PR 规则。
- **模板只在职责缺失时创建。** 沿用项目既有路径和等价结构，旧文档随当前任务渐进完善；不为填满模板创建整套 Release 文件。

## 按文档填写

### 需求概要

围绕真实问题和已确认意图写概要：为什么做、为谁做、做什么、不做什么、有哪些总体约束、如何判断有价值。成功指标写口径与依据；尚无量化指标时明确标注，以可观察结果表达验收目标。保留需求版本、冻结状态、确认依据和阻塞问题入口，不在这里复制逐功能 AC 或技术实现。

### 产品需求文档（PRD）

按模板九章展开。背景、目标与用户先各写可独立阅读的简述，再链接 BRIEF；功能表使用既有 REQ 编号及优先级，不再平行建立 FEAT 编号。实现状态和测试结果留在进度与验证记录。

每项核心功能写明使用前提、主流程、输入与校验、业务规则、适用权限、异常与恢复，并列出关联 REQ 的 AC。AC 使用“给定条件—当执行操作—则出现可观察结果”，正常路径与已知异常分支都应可判定，说明从哪里输入、观察什么输出。

- 单一同步交互在 AC 旁写检查入口即可，不另造状态机或接缝长表。
- 多步骤顺序影响结果时补流程；存在异步事件、独立生命周期或转换限制时补状态表，覆盖取消、重试及并发竞态。
- 跨模块或系统验收时补测试接缝（Test Seams），写清触发入口、观察位置和 AC 引用；不重复完整验收描述。
- 有界面的核心流程逐项核对空、加载、错误和极限状态，明确反馈、可用操作及数据保留行为；某状态不适用时说明原因。
- 限制与非功能需求写明口径、边界和验证方法；埋点仅在需求成立时列事件、触发、属性与分析目的。

每项 AC 只能展开已确认行为，不能借示例或模板补定产品含义。缺少且会改变用户可见结果的条件，写入待决问题及受影响验收范围；“已冻结”不授权 Agent 补充这些含义。普通内部实现选择写在方案设计中。

### 方案设计

写本次尚待实现的技术方案及状态，先引用当前技术设计中的相关事实，再写目标和变化。必要细节直接进入正文：

- 技术栈标明复用或新增及版本来源；工程约定链接现有规则，说明目录职责与依赖方向。
- 总体架构写组件边界、核心读写路径和状态传播。共享状态应有唯一写入入口，并说明读取、刷新、失败、取消和恢复路径；未核查的模块不能宣称无影响。
- 有数据变更时列模型、字段类型、约束、默认值、查询与索引；有缓存、迁移或兼容影响时写其策略及恢复限制。
- 有接口变更时写输入输出、校验、权限、错误和兼容；并发、事务、幂等、重试与取消按真实行为说明。
- 每个关键选择说明理由；存在实质备选再比较收益和代价，没有实质备选时说明依据，不编造被弃方案。
- 安全、隐私、日志指标及告警按实际风险填写，恢复写触发条件、动作、数据影响和验证方法。

已有授权继续有效；方案获批与实现完成是两个不同状态。“方案设计”不表示已批准或已实现。

### 当前技术设计

使用相近的技术维度描述已成立的当前事实，为组件、技术栈版本、接口、数据、配置、运行与检查入口给出代码、配置或真实结果定位。区分“有配置”“已执行”“尚未核验”，命令存在不能证明运行成功；无实现的能力不能写成当前架构。

方案设计负责目标与取舍，当前技术设计负责事实。实现并验证后才将成立部分同步到本文件；未实现或不成立部分继续留在方案、待核验项或偏差入口，不混写为现状。

### API 调用文档

当项目提供面向前端、其他服务或第三方的 API、SDK 等调用接口时，维护调用方可直接使用的说明；普通内部函数不因此建文档。优先沿用已有 API 文档、OpenAPI 及生成文档或 SDK 文档，只补缺失的接入说明；没有独立契约源时可由调用文档直接承载契约，不强制引入 OpenAPI 或生成工具。

面向调用方交代接入地址或导入入口、适用版本、认证与权限、参数类型与必填/默认/约束、成功结果和错误含义，提供与实际接口一致的正常及失败调用示例。分页、限流、幂等、重试及兼容限制仅在适用时说明，不借模板新增这些能力；示例使用占位凭证和脱敏数据。已有权威契约时，字段和 Schema 精确引用该源，正文补业务含义、步骤及示例，不平行维护字段表。

调用文档持续维护，不按 Release 复制。未实现接口明确标为计划内容；当前可用范围以代码和实际证据核验，不把本地可用写成已部署。接口实现或修复改变调用行为时，同轮同步契约、说明及受影响示例；生成文档沿用既有生成方式，不直接修改生成物，不默认安装新工具。检查正常与失败示例是否匹配契约，按需复用已有测试、执行生成或示例验证；未运行须如实标明，不因写了示例宣称调用成功。

### 实施计划

按模板六部分写清实施前提与执行路径。文件映射覆盖适用的源码、测试、配置、迁移、脚本和文档，标新增、修改或删除及职责；未知位置标待定位，安排定位步骤，不能捏造精确路径。

每项任务包含编号、交付结果、关联 REQ/AC、依赖、文件、具体步骤、验证命令或操作与预期、恢复依据。共同约束写一次，任务写差异；无有效命令时说明验证方式与当前定位缺口。本次更新的旧计划若已有运行状态字段，将该字段改为进度或验证记录的链接，不再填实际状态值；保留任务、依赖与历史说明，不重写其余章节。

- 按真实依赖与可验证业务闭环拆分，不固定采用数据库、服务、API、UI 的横向阶段。多个闭环才增加切片映射。
- 标出任务依赖及当前就绪前沿（Ready Frontier）；任务状态明细由 PROGRESS 维护。
- 验证矩阵连接 PRD AC、验证场景、测试或操作入口与 Task；实际结果链接 VERIFICATION，不在计划复制通过状态。
- 发布与恢复按实际交付目标填写；分支、提交、部署等操作遵循已有授权，不由模板额外授权。
- 里程碑描述预期达成条件；实际日期、偏差、证据在 PROGRESS/VERIFICATION 留一份记录，再引用回来。设计变化同步对应事实 owner。
- 真正委派复杂任务前按 [Task Handoff Contract](execution.md#task-handoff-contract-统一任务派发契约)组装范围、上下文、风险、证据与恢复点。计划可引用既有内容，不能因简化展示漏掉交接事实。

### 进度

标题后用简短摘要回答当前事实、缺口和下一步；使用表格时最多三条数据行。摘要定位下方记录，不复述全部任务或证据。

只有一个任务时一段记录可承载状态、证据和下一步；多个任务用一张表维护状态，必要时增加证据覆盖说明。确有切片或熔断时再添加相应清单或 Debug Snapshot，不预置空记录。

## 写完与修改时检查

先检查准确与完整，再删除重复并统一形式：

- 小更新只检查改动部分、受影响引用与相邻上下文，保留人工说明及历史。
- 实质修改检查标准章节中所有适用内容：核心功能能否据此验收，设计能否据此实现，任务能否据此执行；不能只凭字数或标题齐全判断完成。
- 删除未替换占位符、空表与不适用章节；需要决定的未知明确记录，不编造成功、优先级、数字或技术能力。
- 核对需求、AC、设计、任务及验证入口的连接；不重复状态，不把计划写成当前事实，不改写历史路径或机器状态。
- 范围或重大取舍有变化时沿用已有 Gate；表达与排版问题自行修正，不增加逐篇审批。
