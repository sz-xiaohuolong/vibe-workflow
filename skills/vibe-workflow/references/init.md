# 项目接入与规则合并

## 何时读取

用户要求 `$vibe-workflow init`、首次接管已有仓库、重建文档索引、核对当前基线，或空仓库新项目获准进入 Planning 时读取。`init` 是 Agent 按 Skill 执行的对话协议，可重复执行，不需要新 CLI、后台服务或额外工具；不代表需求冻结、业务实现或发布授权。

| 场景 | 写入时机与边界 |
|---|---|
| 已有仓库正常 init | 先读规则与现有文档入口，再合并通用约定及必要入口；用户已授权，不重复询问是否可添加 |
| 空仓库直接启动新项目 | 首轮 Thinking 不创建规则文件、工程文档、脚手架或代码；范围与验收确认且获准进入 Planning 后，自动最小接入，正式实现前完成 |
| 明确只读审计或不修改文件 | 只读优先，只报告建议目标与差异，不创建或更新任何文件 |
| Tiny、普通 Git、临时目录单点任务、普通恢复 | 不因空目录、缺规则或缺地图而自动初始化；已有精确请求不升级为新项目 |

## 规则入口定位

写入与恢复共用以下定位顺序；先读取宿主实际适用的上级规则及当前修改范围内的规则，再检查项目现有规则文件、README、唯一 Document Map 和明确指令：

1. 优先沿用项目已明确采用的入口，可为 `AGENT.md` 或 `AGENTS.md`，不重命名。只有一个现有规则文件时沿用该文件；两个都存在时按已有入口声明、地图与实际职责确定接入目标，保留另一个文件的人工内容及独立用途，不复制一套相同约定。
2. 没有既有入口时，用户明确指定上述文件名则采用；否则在项目根目录采用 `AGENTS.md`。不修改项目外的上级规则文件，不为兼容名称生成第二份职责重复的文件。
3. 两个现有文件的职责或入口声明实质冲突、无法确定目标时，保留现状，报告具体分歧；可以继续只读审计和无冲突工作，仅将入口选择作为待确认决定，不猜选、不覆盖。
4. 文件名兼容不等于所有宿主都会自动加载该文件；自动发现范围与优先级遵循宿主实际机制。宿主未自动发现已采用入口时，按现有提示或地图显式读取，不擅自新建重复文件来假定兼容。

将实际相对路径登记在已有 Document Map 的 Agent 规则职责行，并在规则文件补必要的真实地图/恢复入口。尚无地图时，新项目先不写不存在的链接；后续建立唯一地图时双向补入口。下一会话先按同一定位规则找真实文件，不能只查默认 `AGENTS.md`。

## 通用约定的最小合并

公共正文只维护在 [AGENT_RULES.md](../assets/templates/AGENT_RULES.md)。每次写入前读取目标文件、适用规则、已登记入口和该模板，按条款语义核对：

1. 目标不存在且无规则冲突时，完整写入模板。文件只维护行为、入口和边界；地图、命令与目录等项目信息仅在已核验后补充，不猜技术栈、分层、实现或验收状态。
2. 目标已存在时，将模板条款分为“已有语义等价内容”“缺失”“实质冲突”。等价内容保留原文；部分覆盖时只补缺失含义；缺失内容放入相关原章节或一个简短补充章节，不机械追加整篇模板。保留人工内容、项目特有约束、语言偏好、命令及目录规则。
3. 明确的项目规则和用户要求优先于通用模板。实质冲突时保留原文、不追加相反条款，报告原规则位置、模板条款及未合并的具体差异；其余无冲突缺口继续处理。与适用上级规则冲突时同样处理；模板不改变宿主指令优先级。
4. 可选维护区域标记仅帮助定位，不代表拥有或可以覆盖区域内的内容。已写入条款和区域内的人工修改都须逐项核对；不能确认的来源、删除意图或变更保持原样，不整块替换、不据当前模板重置文件。
5. 后续 init 只处理可确认的缺口或变化；不建立版本注册、哈希数据库或规则管理系统。模板更新不会自动批量改写历史项目，等各项目下次 init 时再核对。没有变化时保持文件字节不变，不刷新日期、重排或追加“已同步”记录。

## 已有仓库审计与映射

1. 按上述定位读取规则，核对工作树、分支和相关提交；识别 README、依赖、构建/测试命令、代码入口、部署配置及现有需求、设计、决策、进度、Bug、测试和发布文档。只采样足以判断职责与当前状态的证据，不默认读完整历史。
2. 按内容与用途确定各职责的真实 owner。`specs/`、`docs/architecture.md`、Issue/ADR 和已有进度文档均可沿用；路径名称不决定事实所有权。代码/测试只证明当前实现，不反推历史产品意图或验收批准。
3. 优先更新已有的 `PROJECT.md` Document Map、`DOCUMENT_MAP.md` 或等价索引。仓库没有地图时，在根目录创建 `DOCUMENT_MAP.md`，使用[地图模板](../assets/templates/DOCUMENT_MAP.md)。一个仓库只保留一个权威地图；已有多个时标出冲突，沿用明确采用的入口，不静默覆盖。地图只导航职责、实际路径、状态和依据，不复制业务正文。
4. 正常 init 按最小合并协议补规则与真实入口。只为当前恢复必需且确实缺失的职责补最小文档；不为凑模板创建空 PRD、SPEC、Release 或把需求标为 FROZEN。没有可靠需求写“待澄清”，只有代码事实写“当前实现待确认”。
5. 基于事实更新已有 PROGRESS 或建立最小进度记录；Current Workflow State、Release ID、Last Stable Commit 逐项核验，未知写“待核验/未建立”。
6. 简短报告规则文件真实路径、保留/补充/冲突条款、沿用或新建的地图、事实源、检查及结果、未知与阻塞、下一 Gate/Task。后续业务工作仍遵守原需求门禁、有效证据复用、个人发布与证据预算。

## 新项目最小接入

确认这是从零建立持续开发的项目，且范围与可测验收已确认、获准进入 Planning 后，直接复用已有明确范围与授权，不额外要求 init 或另一轮确认。先按同一定位与合并协议建立最小规则文件，再进行工程规划；正式实现前核对文件已写入。

这里只接入必要规则，不执行存量仓库的全量接管，也不为规则接入预建文档套件。Planning 按 [Artifact 模型](artifacts.md) 沿用或按需建立唯一文档入口，并把真实规则路径登记其中；未建立的技术方案、目录、命令和验收结果不得写成当前事实。完整 Release 的工程入口 Gate 不变。

## 重复执行

再次 init 时先读真实规则入口与已有地图，核对路径、职责及证据是否变化；按条款语义只补缺口，保留人工修改和已发布历史。相同输入与模板不产生重复段落、审计记录、时间戳或无意义 diff；不重复创建目录、台账或并列的 `docs/vibe/`。地图不能替代其指向的规格、设计、代码或证据。
