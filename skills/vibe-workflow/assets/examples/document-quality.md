# 文档写作正例与反例

以下均为虚构片段，用于比较写法，不是实际项目证据，也不能代替[完整模板](../templates/)。示例假定其中产品行为已经确认；正式写作应使用真实范围、文件与证据。事实职责见[文档治理](../../references/artifacts.md)，适用条件见[写作规范](../../references/document-quality.md)。

## 需求概要：明确问题与确认基线

反例：“打造行业领先的智能搜索平台。”没有说明谁遇到什么问题，也没有区分目标和待决定事项。

正例：

```markdown
# 需求概要：本地标题搜索

录音使用者在已加载的列表中难以快速找到记录。本次在原列表增加本地标题筛选，减少手动翻找。

- 目标用户：查找个人录音的使用者。
- 范围：标题筛选、清空恢复与无匹配提示；不接云搜索、不搜索正文、不修改记录。
- 验收目标：能按已确认的匹配规则找出记录，清空后恢复原顺序与内容。
- Requirement Status: FROZEN。
- 确认依据：正式项目在此引用实际批准记录；本片段仅作虚构示例。
- 量化效率收益：尚无测量数据，不能承诺提升百分比。
```

概要保留问题和范围，具体匹配规则、异常与 AC 由 PRD 展开。

## 产品需求文档：行为可判定

反例：“系统应具备优秀的搜索体验。”或整章只写“见概要”，让读者继续查找具体规则。

正例，节选标准 PRD 的背景与功能章节：

```markdown
# 产品需求文档（PRD）：本地标题搜索

## 1. 产品概述与背景

已加载录音列表缺少标题筛选，用户需要逐条翻找。本次在现有列表上提供本地筛选入口。概要基线：PROJECT_BRIEF.md 的范围与验收目标。

## 5. 核心功能详细规格与验收标准

### REQ-001：按标题过滤列表

前提：列表已有加载结果，用户仅能查看原有可见记录。

主流程：输入查询 → 按已确认规则筛选 → 展示结果；清空查询 → 恢复原列表。

规则：去除查询首尾空白后按标题包含匹配，不区分英文大小写；空查询显示全部记录。筛选不修改原记录或顺序。
异常：无匹配时显示“未找到匹配的记录”，保留查询和清空入口。

| AC | 给定条件 | 当执行操作 | 则出现可观察结果 | 检查入口 |
|---|---|---|---|---|
| AC-001 | 列表含“周会”和“Review” | 查询“  review  ” | 仅显示“Review”，原数据不变 | 过滤函数输入输出与页面结果 |
| AC-002 | 当前查询无匹配 | 清空查询 | 无匹配提示消失，全部记录按原顺序恢复 | 页面查询与清空操作 |
```

这段假定“包含匹配”等规则已被确认。真实输入缺少匹配含义时，应记录待决问题，不能照搬示例补定。单一同步筛选不需要额外状态机；有界面时仍按模板逐项核对适用状态。

## 方案设计：解释选择及影响

反例：“新增搜索服务、分布式索引和多级缓存。”输入只要求本地标题搜索，却自行扩大架构。

正例，节选方案与接口章节：

```markdown
# 方案设计：本地标题搜索

Status: PROPOSED。当前页面没有查询框，以下是待实施方案。

推荐复用现有列表，在客户端过滤内存记录。数据已经加载且只搜索标题，无需新增服务或依赖。

## 3. 总体架构

查询输入 → 无副作用的过滤函数 → 现有列表。原列表只读，清空走同一路径。

## 4. 详细设计

过滤接口接收只读记录列表和查询文本，返回匹配记录的原序列子集；每条记录使用已有标题字段。不写入存储，不改变已有权限。空查询返回全部记录，无匹配返回空列表，由页面展示约定提示。

路径尚未定位：实施首步核对现有列表与过滤入口，再填写文件映射。没有新增数据表、缓存或网络接口。

## 5. 选择理由

选用本地筛选，因为本次只处理已加载标题。当前没有需要比较的实质备选；云端索引属于本次非目标。

## 风险、恢复与验证

真实最大数据量未知，尚无容量或响应时间承诺。接入出现回归时撤回查询接入，恢复原列表展示；验证匹配、清空、顺序和原数据不变。
```

正式方案还应填写适用的技术栈、工程约定和其他详细契约。短摘要不能代替这些章节。

## 当前技术设计：每项事实有依据

反例：“当前已接入统一搜索与缓存。”实际只有一份尚未实现的目标方案。

正例：

```markdown
# 当前技术设计：本地录音列表

现有列表读取本地记录并展示，标题筛选尚未实现。该结论来自本次代码核对，不代表页面已运行验收。

| 当前事实 | 依据 | 核验范围 |
|---|---|---|
| 列表读取已有记录 | 正式项目填写实际列表组件和读取函数路径 | 静态代码核对 |
| 没有标题查询入口 | 同一组件的输入与渲染分支 | 静态代码核对 |

后续方案见 PROPOSED_DESIGN.md；实现与验证后再同步成立部分。实际文件和运行命令尚未核验时应保持未知，不用示例路径充当证据。
```

表中的依据在正式文档中必须替换为真实定位；当前事实与未核验项分开。

## 实施计划：文件、步骤与验收相连

反例：“先完成后端，再完成前端，覆盖率达到 85%。”没有依据、文件、执行入口和预期结果。

正例，节选单任务记录：

```markdown
# 实施计划：本地标题搜索

先定位入口并实现过滤，再接入查询与清空操作，最后完成交互验收。关联 REQ-001 / AC-001、AC-002；只修改列表筛选及对应测试。

## TASK-001：实现可验证的标题筛选

- 交付结果：无副作用的筛选函数，满足 AC-001 与 AC-002 的数据规则。
- 依赖：无；页面接入任务依赖本任务。
- 文件：现有过滤入口及其测试文件待定位；先查找列表读取和现有测试约定，再补入文件映射。
- 步骤：定位入口 → 按已确认规则实现过滤 → 补充匹配、空查询、空结果和原数据不变的用例。
- 验证：沿项目已核验的相关测试命令运行上述用例；命令尚未定位，不编造可执行指令。
- 预期：结果只含匹配项，原记录及顺序不变，空查询恢复全部项。
- 恢复：撤回本任务的过滤接入，保留既有列表行为；定位后登记实际恢复基线。

当前就绪任务：TASK-001。实际状态与结果见 PROGRESS / VERIFICATION，不在本计划再维护一份。
```

任务有未知时先安排定位，不能停留在“按需实现”。正式实施计划还需文件映射、验收矩阵及适用的发布恢复预案；真正委派复杂工作时再组装完整交接契约。

## 进度：当前事实、缺口和下一步

反例：“搜索能力全面推进，整体顺利，后续持续加强测试与体验。”

正例：

```markdown
# 进度：本地标题搜索

| 当前事实 | 缺口 | 下一步 |
|---|---|---|
| 过滤逻辑已实现，局部单测通过，见 TASK-020 | 页面交互未验证 | 接入查询框并验证组合输入和清空 |

## TASK-020

状态：IMPLEMENTED_UNVERIFIED。现有单测 3/3 通过仅覆盖过滤逻辑；页面接入未完成。
证据：E-01，来源为本次输入中的既有测试记录，正式项目在此链接实际报告。
```

结论与证据覆盖范围一致，缺口可见。只有一个任务时不再复制任务表、切片表和验收覆盖表。
