# 文档写作正例与反例

以下均为虚构片段，用于展示写法，不是实际项目证据或完整模板。事实职责见 [文档治理](../../references/artifacts.md)，裁剪条件见 [写作规范](../../references/document-quality.md)。正式写作应填入真实来源与证据定位。

## 需求分析：行为可判定

反例：“系统应具备优秀的搜索体验，充分满足用户的多样化查询需求。”随后又用流程图、状态表重复同一过滤操作。

正例：

```markdown
# 需求分析：本地标题搜索

仅搜索已加载记录的标题，不接入云搜索。验收见 AC-001、AC-002。

## REQ-001：按标题过滤列表

- AC-001：查询去除首尾空白后按标题匹配，不区分英文大小写；空查询显示全部记录。
- AC-002：无匹配时显示“未找到匹配的记录”；清空后立即恢复完整列表，原记录及顺序保持不变。

验收入口：过滤函数测试和页面查询/清空操作。两项结果均满足后才能判定完成。
```

修改理由：把抽象评价改成可观察结果。同步过滤用行为与 AC 即可，不另设独立状态机。

## 方案设计：解释选择及影响

反例：“为构建高可用搜索体系，新增搜索服务、分布式索引和多级缓存。”输入仅要求本地标题搜索，却引入未确认架构。

正例：

```markdown
# 方案设计：本地标题搜索

推荐复用现有列表，在客户端过滤内存记录。数据已经加载且只搜索标题，无需新增服务或依赖。

状态：PROPOSED。当前页面没有查询框，以下是待实施方案。

查询输入 → 过滤函数 → 现有列表；清空输入复用同一路径。
原列表只读，不改存储与权限。若接入导致回归，撤回查询接入，恢复原列表展示。

真实最大数据量未知，尚无容量或响应时间承诺。按需求分析的 AC 验证匹配、清空及原数据不变。
```

修改理由：先给推荐方案和理由，再交代影响、恢复及未知。方案名称不能替代状态标记。

## 实施计划：看清顺序与验收

反例：三个普通任务各复制一整套相同的上下文、风险标签、无影响模块和恢复说明，即使没有委派。

正例：

```markdown
# 实施计划：本地标题搜索

先实现过滤，再接入页面，最后完成交互验收。关联 REQ-001 / AC-001、AC-002。
修改范围仅为既有过滤逻辑、列表组件及对应测试；恢复依据为接入前的列表展示路径。

| 任务 | 交付 | 依赖 | 验证 |
|---|---|---|---|
| T1 | 过滤函数 | 无 | 匹配、空白查询及源列表不变 |
| T2 | 查询框和清空操作 | T1 | 中文输入法、清空恢复与提示文案 |

当前就绪任务：T1。若后续委派复杂工作，再按执行协议组装完整交接契约。
```

修改理由：共同事实只写一次，任务表突出差异。正式计划中的恢复依据与检查入口仍须核验。

## 进度：当前事实、缺口和下一步

反例：“搜索能力全面推进，整体顺利，后续持续加强测试与体验。”

正例：

```markdown
# 进度：本地标题搜索

| 当前事实 | 缺口 | 下一步 |
|---|---|---|
| 过滤逻辑已实现，局部单测通过，见 TASK-020 | 页面交互未验证 | 接入查询框并验证组合输入和清空 |

## TASK-020

状态：IMPLEMENTED_UNVERIFIED。现有单测 3/3 通过仅覆盖过滤逻辑；页面接入未完成。
证据：E-01，来源为本次输入中的既有测试记录，正式项目在此链接实际报告。
```

修改理由：结论与证据覆盖范围一致，缺口可见。只有一个任务时不再复制任务表、切片表和验收覆盖表。
